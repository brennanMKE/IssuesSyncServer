## Description

Review the passkeys/WebAuthn design doc from the sibling ShortLinks project
(`../ShortLinks/docs/passkeys.md`) and audit the WebAuthn/PassKey support
currently prepared in this project (Phase B `internal/auth/`) against it.
ShortLinks is a more mature Go + `go-webauthn` deployment whose doc captures
several hard-won lessons; the goal is to confirm `issued` either already handles
each of them or has an issue tracking it.

The ShortLinks doc covers, and this audit should check our equivalent for:

- **RP configuration** — exact-origin / HTTPS / Secure Context requirements.
  Confirm our `BASE_URL` / `RP_ID` / `RP_DISPLAY_NAME` wiring into
  `webauthn.New` matches (no scheme/port/trailing-slash drift, `RPOrigins`
  set correctly).
- **Registration / login / recovery ceremonies** — challenge persistence with
  TTL + single-use consumption (replay prevention), generic "account existence
  never revealed" responses, discoverable vs. scoped `allowCredentials` login.
- **Backup-Eligible (BE) / Backup-State (BS) flags** — the big one. ShortLinks
  issue #0047 showed that failing to persist BE at enrollment and rehydrate it
  at assertion makes *every* iCloud Keychain login fail with "Backup Eligible
  flag inconsistency". Verify our credential model stores `backup_eligible` /
  `backup_state` and rehydrates them before `ValidateLogin`.
- **Sign-count handling** — synced passkeys report `sign_count = 0` on both
  sides; confirm we don't emit spurious clone warnings for that case.
- **Binary encoding** — unpadded base64url (`base64.RawURLEncoding`) on the wire
  for all credential binary fields.
- **First-admin enrollment** — how the `ADMIN_EMAIL` bootstrap user actually
  enrolls a passkey (ShortLinks routes the seeded admin through the recovery
  flow, since registration rejects already-registered emails).

## Expected outcome

A written assessment of where `issued`'s passkey support aligns with the
ShortLinks doc, a list of gaps or risks (especially the BE/BS persistence issue),
and follow-up issues filed for anything missing. Note that ShortLinks uses
session cookies for a web client while `issued` issues JWT access + opaque
refresh tokens for a native Mac client, so some divergence is expected and by
design — focus the audit on the WebAuthn ceremony mechanics, not the token model.

## Notes

Reference doc lives outside this repo at `../ShortLinks/docs/passkeys.md`.
This is a review/audit task, not a bug report — file separate issues for any
concrete defects it surfaces.
